주식 거래소의 주문 접수와 체결을 작게 구현하고, 거래 요청이 늘 때 어디서 무엇이 막히는지 단계적으로 재는 학습 프로젝트입니다. 실제 증권사 주문은 넣지 않고, KRX 데이터는 종목 정보로만 씁니다.

원칙은 하나입니다. **기능 구현 → 측정 → 병목 관찰 → 그다음에 기술 도입.** 큐나 쿠버네티스는 측정으로 필요가 확인되기 전까지 넣지 않았고, 매번 측정 조건과 해석 한계를 보고서로 남겼습니다.

## 어떻게 만들었나

코드는 AI 코딩 에이전트가 작성했고, 결과 해석과 보고서 정리도 에이전트와 함께 했습니다. 제가 붙잡은 것은 질문과 판단이었습니다. 특히 운영체제와 백엔드 쪽에서 두 가지를 오래 고민했습니다.

- 하드웨어 CPU 사용률을 어떻게 끝까지 끌어올릴 수 있을까?
- VM에 코어가 여러 개인데, 왜 여러 코어를 동시에 쓰지 못할까?

## 왜 코어를 다 쓰지 못했나

| 원인 | 무슨 일이었나 | 확인한 방법 | 택한 방향 |
|---|---|---|---|
| Python GIL | 한 프로세스 안에서 파이썬 코드는 한 번에 한 스레드만 실행됩니다. Gunicorn 스레드를 4개로 둬도 CPU 일은 코어 하나에 모입니다. | 프로세스 하나의 CPU가 1코어에서 멈춤 (Day 4에서 샤드당 0.98–0.99) | 스레드가 아니라 프로세스를 늘린다 |
| 인메모리 호가창 | Gunicorn `--workers 2`로 프로세스를 늘리면 같은 종목의 호가창이 두 벌로 갈라집니다. 매수와 매도가 다른 프로세스에 들어가면 체결이 안 됩니다. | 설계 단계에서 배제 | 종목 단위로 나눠 프로세스마다 다른 종목을 맡긴다(샤딩) |
| 공유 코어 VM | `e2-medium`은 vCPU 2개로 보이지만 지속적으로 쓸 수 있는 건 물리 코어 약 1개 분량입니다. | 두 샤드의 CPU 합이 2.0에 못 미친 채 접수 품질이 무너짐 | 지속 4 vCPU인 `e2-standard-4`로 변경 |
| 코어와 프로세스 수 | 4 vCPU에 샤드 2개면 2코어가 놉니다. 샤드를 4개로 늘리자 이번엔 네트워크 ACL에 막혔습니다. | 바깥에서 샤드 2·3이 타임아웃 | 종목 라우터 하나를 진입점으로 두고, 샤드 4개는 VM 안에서만 듣게 |

그리고 CPU를 다 쓴다고 처리량이 오르는 것도 아니었습니다. Day 3에서 CPU는 1.5에서 1.9로 올랐는데 초당 주문은 139건에서 17건으로 떨어졌습니다. 호가가 두꺼워져 주문 한 건이 더 비싸졌기 때문입니다. **사용률은 결과일 뿐이고, 한 건에 드는 일의 양을 같이 봐야 한다**는 게 이 프로젝트에서 얻은 가장 큰 교훈입니다.

## 구성

```
mini PC (home)                          GCE e2-standard-4
  participant-runner ---Tailscale--->  :8000  symbol router
                                          +--> 127.0.0.1:8001  shard 0
                                          +--> 127.0.0.1:8002  shard 1
                                          +--> 127.0.0.1:8003  shard 2
                                          +--> 127.0.0.1:8004  shard 3
  Prometheus, Grafana <---scrape-----  :8000/metrics/{shard}
  PostgreSQL 17 <------Tailscale-----  shards
```

집의 미니 PC에서 트레이더(runner)가 Tailscale로 GCE의 종목 라우터 하나에만 주문을 보냅니다. 라우터는 종목을 보고 VM 안에서만 열린 매처 샤드 4개 중 하나로 넘깁니다. 관측과 DB는 집에 있습니다.

- **매칭 엔진:** Django/DRF. 종목별 인메모리 호가창, 가격·시간 우선, 부분 체결. 같은 종목은 프로세스 하나만 처리합니다.
- **시장참여자:** 백엔드와 분리된 runner가 HTTP로 주문합니다. Noise, Momentum, Mean Reversion, Liquidity Provider 전략, 거래대금 상위 10종목.
- **인프라:** Terraform으로 VPC, GCE, Artifact Registry, Secret Manager를 만들고, GitHub Actions는 OIDC(Workload Identity)로 인증해 키 파일 없이 배포합니다. 백엔드 포트와 DB는 공인망에 열지 않고 Tailscale 안에서만 오갑니다.
- **관측:** Prometheus와 Grafana. 골든 시그널 대시보드와 SLO 알림 규칙.

## 닷새 동안 바꾼 것과 결과

각 날짜의 조건, 숫자, 해석 한계는 저장소의 `report/`에 있습니다.

| 날 | 바꾼 것 | 결과 |
|---|---|---|
| Day 1 | 5종목, 트레이더 2,000명 | 원격 DB 조회가 주문마다 들어가 처리량이 절반으로 줄었습니다. 기동 시 캐시로 고쳐 주문 평균이 38ms에서 1.8ms로 돌아왔습니다. 남은 한도는 백엔드가 아니라 runner의 직렬 HTTP였습니다. |
| Day 2 | runner 동시 전송, 매처 2개 샤드 | 두 코어를 고르게 쓰게 됐지만 초당 주문은 약 120건으로 거의 그대로였습니다. **샤딩의 효과는 CPU 분배였지 처리량 증가가 아니었습니다.** |
| Day 3 | 동시성 64, 틱 250ms | 호가 잔량이 1.1만에서 190만까지 쌓이면서 초당 주문이 139건에서 17건, p50이 3.5ms에서 300ms로 무너졌습니다. CPU는 더 쓰는데 처리량은 떨어졌습니다. 병목은 호가의 두께였습니다. |
| Day 4 | VM을 공유 코어에서 4 vCPU로 수직 확장 | 접수는 회복했지만(약 130건/s) 잔량이 분당 1.4만씩 다시 늘었습니다. **하드웨어로는 증상을 늦출 뿐이었습니다.** |
| Day 5 | 종목 라우터를 단일 진입점으로, 매처 4개는 loopback만 | 3일 연속 초당 약 146건, p50 2.7ms, p99 19ms, 5xx 0. 잔량도 평평했습니다. 대신 메모리가 255MiB에서 4.3GiB로 꾸준히 늘어나는 새 신호가 보였습니다. |

## 측정하면서 알게 된 것

- **병목은 계속 자리를 옮깁니다.** runner의 직렬 전송 → 단일 프로세스 → 호가 두께 → 메모리. 하나를 풀면 다음이 보였고, 그래서 매번 다시 쟀습니다.
- **더 넣는다고 빨라지지 않습니다.** 동시 전송을 32에서 128로 올리자 줄만 길어지고 처리량은 오히려 줄었습니다. 서버 쪽 동시 실행 수가 4인데 128을 밀어 넣은 셈입니다.
- **평균보다 꼬리를 봅니다.** p99가 220ms 근처에 붙어 있던 것은 실제 지연이 아니라 Prometheus 기본 버킷 경계였습니다. 히스토그램 버킷 한계를 해석에 같이 적었습니다.
- **네트워크도 결과를 바꿉니다.** 샤드를 늘렸는데 Tailscale ACL이 포트 8000, 8001만 열려 있어 나머지 샤드는 바깥에서 보이지 않았습니다. 포트를 더 여는 대신 종목 라우터 하나로 진입점을 모아 해결했습니다.

## 운영

- 이 백엔드는 실험할 때만 띄웁니다. 비용 때문에 GCP 인프라를 철거한 뒤에도 같은 환경을 다시 세울 수 있도록, 복구·계정 이전·안전한 철거 절차를 runbook으로 남겼습니다.
- DB는 Cloud SQL 대신 집의 PostgreSQL을 Tailscale로 연결했습니다. 주문 경로에 DB가 없는 단계라서 가능한 선택이었고, 주문을 영속화하는 단계가 오면 다시 검토하기로 했습니다.
