LLM에 DM 답장을 맡기는 것 자체는 쉽습니다. 어려운 건 그 뒤입니다.

- 모델이 답장을 쓰는 동안 새 메시지가 오면? 같은 메시지에 두 번 답하면?
- 전송이 타임아웃으로 끝났는데 실제로는 나갔다면? 다시 보내면 중복입니다.
- 모델이 "보냈다", "저장했다"고 말했지만 실제로는 실패했다면?

이 프로젝트는 이런 문제를 모델의 성실함에 맡기지 않고, 코드와 데이터베이스 제약으로 해결하는 데 집중했습니다. 전체 코드는 홈랩의 개인 Gitea에서 관리하고, GitHub에는 컨트롤러 코어만 분리해 공개했습니다. 운영 설정과 인증 정보, 실제 대화 기록은 넣지 않았습니다.

## 어떻게 만들었나: AI 코딩 에이전트와 함께

이 프로젝트의 코드는 AI 코딩 에이전트로 구현했습니다. 코드는 에이전트가 쓰고, 구조와 방향은 제가 정하는 식으로 나눴습니다.

| 누가 | 무엇을 |
|---|---|
| 제가 | 시스템을 모듈로 나누는 구조, 나눈 작업을 난이도별로 다른 모델에 배정하는 방식, 비용을 줄일 방향 |
| 에이전트가 | 코드 작성, 테스트 작성과 실행 |
| 제가 | 테스트 결과와 실제 동작을 보고 반영할지 판단 |

- **모듈로 나누고, 작업 난이도에 맞는 모델을 쓴다.** 생활 판단, 대화 방향, 문장 작성, 검토를 서로 다른 역할로 떼어 내고, 역할마다 난이도에 맞는 모델을 배정할 수 있게 만들었습니다. 어려운 판단에만 비싼 모델을 쓰자는 생각이었습니다. 다만 실제 플랫폼에서 돌려 보니 지연과 품질 문제가 생겨서, 지금은 이 구조를 설정으로 꺼 두고 있습니다(아래 플랫폼별 운영 참고).
- **토큰을 줄일 곳도 에이전트에게 찾게 한다.** 운영하면서 쌓인 사용량을 보고, 줄일 수 있는 부분을 찾아 달라고 에이전트에 맡긴 뒤 제안을 검토해 반영합니다.
- **테스트는 에이전트가 쓰고 돌린다.** 테스트 파일 60여 개를 에이전트가 작성하고 실행하며, 저는 그 결과를 보고 판단합니다.
- **새 기능은 꺼진 채로 들어온다.** 새로 만든 기능은 기본 꺼짐으로 두고, shadow 모드로 먼저 관측한 뒤 켭니다.

이 프로젝트가 다루는 문제와 만든 방식은 같은 구조입니다. 대화 모델의 출력을 그대로 믿지 않고 코드로 검증하듯, 코딩 에이전트의 출력도 테스트 결과로 확인하고 반영했습니다.

## 구조

```
메신저 수신 → ingest → SQLite 원장 ← apply (결정 검증, 원자적 반영)
                          │                     ▲
                          ▼                     │
                     gate (깨울지 판단)     decision_session
                          │              (입력 준비 → 판단 → 검증 → 커밋)
                          ▼                     │
                     모델 워커 (외부 LLM) ──────┘
                          │
                     dispatch (발송 lease, 순서, 재시도) → 메신저 전송
```

## 설계 원칙

### 모델 출력은 제안이고, 반영은 코드가 한다

모델은 JSON 결정을 제출하고, `store.apply`가 활동 시간 충돌, 고정 일정, 대상 메시지 ID, 초안 일치 여부를 검사합니다. 하나라도 어긋나면 결정 전체를 롤백합니다.

### "보냈다"는 증거가 있을 때만 사실이 된다

발송 결과를 `confirmed`, `submitted`, `unknown`, `failed`로 나눕니다. `unknown`은 자동으로 다시 보내지 않고, 확인된 발송만 "내가 한 말" 기억이 됩니다. 발송은 OS 파일 잠금과 작업 lease로 한 번에 하나만 나가게 하고, 429 응답이 오면 차단합니다.

### 판단 도중 들어온 메시지를 잃지 않는다

입력을 준비한 뒤 새 메시지가 오면 revision이 바뀝니다. 새 수신만으로 생긴 변화는 구분해서, 이미 쓴 답장은 그대로 보내고 늦게 온 메시지는 다음 판단으로 넘깁니다.

### 기억 검색은 측정한다

배경 사건 기억은 BM25에 중요도 감쇠와 최근성 감쇠를 더해 순위를 매기고, 오프라인 recall 평가 도구로 변경 전후를 비교합니다.

### 모든 확장은 기본 꺼짐

역할 분리, 배경 기억, 반복 방지, 인물 문서 갱신은 모두 설정으로 켭니다. 기존 경로를 바꾸지 않고 shadow 모드로 먼저 관측한 뒤 enforce로 전환합니다. 인프라에서 새 기능을 카나리로 내보내는 것과 같은 방식입니다.

## 토큰 사용량 측정: 줄인 것과 늘어난 것

답장 지연과 품질은 Grok Bot이 가장 좋지만 비용도 가장 높아서, 품질을 지키면서 사용량을 얼마나 줄일 수 있는지가 핵심입니다. 모델 제공자의 호출별 사용량 내보내기를 컨트롤러의 판단 기록(`decision-trace`) 시각에 맞춰, 토큰이 어느 단계에서 나가는지 나눴습니다. 전체 분석은 [token-usage-analysis.md](https://github.com/grademe12/dm-roleplaying/blob/main/operations/token-usage-analysis.md)에 있습니다.

### 바꾼 것

- 모델이 직접 깨어나 할 일을 확인하던 것을, 모델 없는 타이머와 `gate`가 정하게 함
- 입력을 목록과 본문으로 나눠, 필요한 문서만 이어 읽게 함
- 연달아 오는 DM을 묶어 한 번에 판단

### 결과

대화량이 다른 구간을 비교하려고, 시간 단위로 `토큰 = 고정비 + 답장 수 × 답장당 비용`을 나눴습니다.

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| 고정비 | 10.4M / 시간 | **0.38M / 시간** (−96%) |
| 답장당 | 0.57M | **1.40M** (증가) |

- 고정비는 답장이 0건인 시간의 토큰을 직접 평균한 값입니다. 변경 후 0건 시간이 대부분 밤이라, 양쪽 모두 1~7시만 비교해도 −96%로 같았습니다.
- 답장당 추가 비용은 오히려 늘었습니다. 예전에는 이미 깨어 있는 세션이 연달아 오는 DM에 이어서 답했지만, 지금은 답장마다 판단을 새로 만들기 때문입니다.

### 처음 결론을 정정한 과정

처음에는 같은 낮 시간대 총량을 비교해 "72% 줄었다, 판단당 3.0M → 1.4M"이라고 적었습니다. 다시 보니 두 가지가 틀렸습니다.

- **단위:** "판단"으로 센 값이 실제로는 기상 횟수였습니다. 변경 전에는 기상 한 번이 답장 여러 개를 처리해서, 기상당 값은 같은 조건의 비교가 아니었습니다.
- **대화량:** 비교한 날은 대화가 훨씬 적었습니다(답장 280건 → 27건). 답장당으로 보면 1.95M과 1.89M으로 거의 같았습니다.

그래서 단위를 답장으로 바꾸고 고정비와 답장당 비용을 나눴습니다. 위 표의 결론이 그 결과입니다. 총량만 보면 개선처럼 보이는 변화가 실제로는 대화가 적었던 탓일 수 있다는 것, 그리고 무엇을 1건으로 셀지부터 정해야 한다는 것을 배웠습니다. 정정 전후를 모두 문서에 남겨 두었습니다.

### 남은 비용의 원인과 다음 목표

- **같은 문서의 재전송:** 작업 세션에 넘기는 입력은 평균 130KB이고, 그중 80KB는 매번 같은 지침 문서 7개였습니다. 한 기상 안에서 입력을 평균 5.6번 다시 만들어서, 넘긴 바이트의 83%가 재전송이었습니다.
- **호출마다 붙는 맥락:** 작업 세션은 호출할 때마다 약 80K 맥락을 다시 보냅니다. 판단 하나에 호출이 17~23번이라 비용이 "호출 수 × 80K"에 가깝습니다.
- **기억 기능의 비용:** 배경 기억을 켜자 같은 저녁 시간대 기준 답장당 약 0.67M이 늘었습니다. 저녁 총량은 오히려 줄어서 처음엔 늘지 않은 줄 알았는데, 그날 답장 수가 적어 차이가 가려진 것이었습니다.

다음 목표는 고정비를 지금 수준으로 유지하면서 답장당 추가 비용을 변경 전 수준(약 0.6M)으로 되돌리는 것입니다. 이미 받은 문서는 한 줄 생략본으로 보내는 수정을 넣었고, 한 번에 하나씩 바꾸며 같은 방식으로 다시 잴 계획입니다.

같은 흐름을 두고 프로바이더별 성능, 답변 품질, 응답 속도도 비교하고 있습니다. 모델 연결은 OpenAI 호환 엔드포인트 설정 하나로 바꿀 수 있어서, 코드를 고치지 않고 갈아 끼워 볼 수 있습니다.

## 플랫폼별 운영: Meta Muse와 Grok Bot

이 에이전트는 API 서버가 아니라 개인 비서형 에이전트 플랫폼 위에서 돌아갑니다. 처음에는 가장 잘 맞아 보였던 Meta Muse에서 시작했고, 지금은 Meta Muse와 Grok Bot(xAI, Cursor) 두 곳에서 함께 돌리면서 플랫폼 성질에 맞게 구조를 조금씩 다르게 다듬고 있습니다.

| 플랫폼 | 겪은 문제 | 지금 구조 |
|---|---|---|
| **Meta Muse** | 모듈로 나눠 돌리니 모듈마다 세션을 다시 불러와서 답장 지연이 너무 길어졌습니다. | DM 수신부터 발송까지는 한 세션이 처리하고, 기억 정리만 따로 돌립니다. |
| **Grok Bot** | 세션 문제는 비교적 괜찮았지만, 모듈로 나누자 답장 품질이 떨어졌습니다. | 모듈화를 되돌려 DM 수신부터 발송까지 한 세션이 처리하게 하자 품질이 돌아왔습니다. 기억 정리는 여기서도 따로 돌립니다. 지금은 지연과 품질 모두 가장 만족스럽지만 Meta Muse보다 훨씬 비싸서, 토큰 사용량을 줄이는 데 집중하고 있습니다. |

두 플랫폼 모두 모듈화를 되돌렸지만 이유는 달랐습니다. Meta Muse는 지연 때문에, Grok Bot은 품질 때문이었습니다. 설계로는 맞아 보였던 구조도 실행 환경에서 재 보면 답이 달라질 수 있고, 모듈화는 목표가 아니라 수단이라 효과가 없으면 되돌린다는 걸 직접 확인한 부분입니다. 지금의 과제는 품질이 가장 좋은 Grok Bot을 감당할 수 있는 비용으로 돌리는 것입니다.

기억 정리만은 두 플랫폼 모두 끝까지 떼어 두었습니다. 이 모듈은 DM을 받고 보내는 흐름에 끼지 않고 바깥에서 돌면서, 대화 흐름이 읽을 컨텍스트 기억을 정제하고 잊힐 기억을 고릅니다. 답장 지연에 영향을 주지 않으니 나눌 이유가 분명한 곳만 나눈 셈입니다.

## 역할별 모델 선택

모듈로 나눠 돌리던 시기에, 여러 프로바이더를 바꿔 가며 같은 흐름을 돌려 보고 역할마다 품질과 속도, 비용이 맞는 모델을 비교했습니다. 지금 플랫폼에서는 한 세션 구조로 돌리고 있지만, 기억 정리는 여전히 따로 돌아갑니다.

| 역할 | 가장 좋았던 모델 | 비교해 본 것과 판단 |
|---|---|---|
| **write** (답장 문장 생성) | Claude Opus 5.5 (Venice API) | 가장 어려운 역할입니다. 쌓인 컨텍스트와 지침을 모두 읽고 자연스러운 문장을 써야 합니다. Opus 5.5가 가장 빠르고 가장 자연스러웠습니다. OpenAI Astra는 결과물과 비용 모두 기대만큼은 아니었습니다. |
| **기억 정리** | OpenAI 6.1 Terra (high) | 대화 흐름 밖에서 따로 실행합니다. 대화 흐름이 읽을 기억을 정제하고 잊힐 기억을 고릅니다. 6.1 Luna는 토큰을 정말 적게 쓰지만, 기억 정리만 맡겨도 품질이 아쉬웠습니다. OpenCode와 연계해 돌립니다. |
| **이미지** | Seedream, Wan (Venice) | |

- **써 본 프로바이더:** OpenAI, Anthropic Claude, Venice, DeepSeek, Kimi
- **뺀 것:** DeepSeek과 Kimi는 생각보다 토큰 비용이 비싸서 계속 쓰지 않았습니다.
- **설계 단계:** 구조를 잡을 때는 Kiro에서 Opus 5.5를 함께 썼습니다.

정리하면, 비싼 모델의 차이가 가장 크게 드러난 건 문장 생성이었고, 기억 정리처럼 따로 돌리는 작업은 이미 구독 중인 모델로 충분했습니다.
