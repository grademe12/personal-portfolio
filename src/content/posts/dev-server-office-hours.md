## 문제

구름 과정의 마지막 팀 프로젝트(Stagelog)에서 EKS 위에 MSA를 올렸다. AWS 계정은 내 계정 하나에 팀원들을 IAM 사용자로 붙여서 썼다. 그러니 청구서도 전부 내 몫이었다.

개발 환경이라 24시간 켜 둘 이유가 없었다. 우리가 일하는 시간은 평일 9시부터 6시까지였다. 일주일 168시간 중 45시간이다. 나머지 123시간 동안 EKS 컨트롤 플레인, 노드, NAT 게이트웨이가 아무도 안 쓰는데 돈을 내고 있었다.

그런데 매일 끄고 켜려면 조건이 있었다. 끌 때마다 DNS, 인증서, 데이터까지 날아가면 안 된다.

## 수명주기로 스택을 나누기

Terraform 상태를 하나로 두지 않고, "얼마나 오래 사는가"를 기준으로 네 개로 나눴다.

| 스택 | 담는 것 | 언제 내리나 |
|---|---|---|
| `0-ssm-params` | 서비스별 설정값 | 내리지 않음 |
| `1-permanent` | VPC, S3, CloudFront, Route 53, ACM, WAF, 데이터 저장소 | 내리지 않음 |
| `2-eks` | EKS, 노드 그룹, Interface VPC Endpoint | 매일 저녁 |
| `3-ephemeral` | API Gateway, VPC Link | 매일 저녁 |

이렇게 나누면 `2-eks`와 `3-ephemeral`만 내렸다 올려도 도메인, 인증서, 데이터는 그대로 남는다. 상태 파일도 스택마다 따로라서, 매일 하는 destroy가 영구 자원을 건드릴 위험이 없다.

무료인 Gateway Endpoint(S3, DynamoDB)는 영구 계층에 두고, 시간당 과금되는 Interface Endpoint는 EKS와 같이 내리는 계층에 뒀다. 같은 "VPC Endpoint"라도 과금 방식이 다르니 사는 곳도 달라야 했다.

## 매일 올리고 내리기

순서가 중요해서 손으로 하면 실수가 났다. `deploy_all.sh`와 `destroy_all.sh`를 만들고 Makefile로 순서를 묶었다. 올릴 때는 설정값 → 기반 → EKS → 앱 → API Gateway 순서, 내릴 때는 그 반대다. 끝나면 Discord로 알림이 오게 했다. 팀원들은 알림을 보고 작업을 시작했다.

## 얼마를 아꼈나

매일 내리는 계층에 들어 있는 자원을 서울 리전 온디맨드 가격으로 계산했다.

| 자원 | 시간당 |
|---|---|
| EKS 컨트롤 플레인 | $0.100 |
| 관리형 노드 t3.large × 2 | $0.208 |
| NAT 게이트웨이와 공인 IP | $0.064 |
| Interface VPC Endpoint 6종 × AZ 2개 | $0.156 |
| 내부 ALB | $0.023 |
| Bastion t3.micro | $0.013 |
| **합계** | **약 $0.56** |

| 운영 방식 | 한 달 가동 | 한 달 비용 |
|---|---|---|
| 상시 | 약 730시간 | 약 $410 |
| 평일 09–18시 | 약 196시간 | 약 $110 |

한 달에 약 $300 차이다. 표에서 Interface Endpoint가 노드 다음으로 비싼 게 눈에 띈다. "NAT 비용을 줄이려고 Endpoint를 넣는다"는 말을 자주 듣는데, 트래픽이 적은 개발 환경에서는 Endpoint 고정비가 오히려 더 클 수 있다.

## 추정이 맞았는지 청구서로 확인하기

추정은 추정일 뿐이라 실제 청구서를 봤다. EKS 컨트롤 플레인은 시간당 $0.10이라 요금을 시간으로 바꾸기 쉽다.

3월 청구서의 EKS 요금은 $11.04, 약 110시간이었다. EKS를 처음 올린 3월 중순 이후 평일 약 12일 × 9시간과 거의 같다. 24시간 켜 뒀다면 같은 기간에 400시간이 넘게 찍혔을 것이다. 계획대로 운영했다는 것이 청구서로 확인됐다.

## 남은 것

- 추정에는 부하에 따라 Karpenter가 더 띄운 노드와 데이터 전송료가 빠져 있다. 실제 차이는 이보다 크다.
- 운영 환경이라면 끄는 대신 다른 방법을 써야 한다. 예약 인스턴스나 Savings Plans, Spot 비율, 적정 크기 조정이다.

가장 크게 배운 건 순서였다. 비용을 줄이려고 스크립트를 짠 게 아니라, **수명주기대로 나눠 놓으니 끄고 켜는 게 안전해졌고**, 그래서 매일 끌 수 있었다. 설계가 먼저였다.
